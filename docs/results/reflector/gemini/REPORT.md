## Finding 2
- Pattern: Inconsistent Execution Path (Fee Bypass)
- Severity: HIGH
- Location: beam-contract/src/lib.rs:293
- Description: The `twap` function hardcodes the `periods` parameter to 1 when calling `charge_invocation_fee`, bypassing the multi-record fee increment for users calculating a Time-Weighted Average Price over N periods.
- Evidence: In `beam-contract/src/lib.rs`, functions that process multiple historical records, such as `prices`, `x_prices`, and `x_twap`, consistently charge the caller for the number of requested records:

```rust
    pub fn x_twap(e: &Env, caller: Address, base_asset: Asset, quote_asset: Asset, records: u32) -> Option<i128> {
        caller.require_auth();
        charge_invocation_fee(e, &caller, InvocationComplexity::CrossTwap, records);
        PriceOracleContractBase::x_twap(e, base_asset, quote_asset, records)
    }
```

However, the `twap` function performs the same multi-record fetching and computation over `records` but hardcodes `1` into the fee charge function:

```rust
    pub fn twap(e: &Env, caller: Address, asset: Asset, records: u32) -> Option<i128> {
        caller.require_auth();
        charge_invocation_fee(e, &caller, InvocationComplexity::Twap, 1);
        PriceOracleContractBase::twap(e, asset, records)
    }
```

This provides an inconsistent execution path where users can perform expensive N-record TWAP computations while completely bypassing the `period_modifier` fee charge for the extra processed periods.

## Finding 5
- Pattern: Unsafe Sentinel Value
- Severity: HIGH
- Location: oracle/src/events.rs:24
- Description: Using 0 as a sentinel value for missing price updates causes explicitly submitted zero prices to be silently ignored, potentially leaving consumers with stale, non-zero prices during an asset crash.
- Evidence: In `oracle/src/events.rs` lines 24-26, `publish_update_event` skips processing an asset if `price == 0`. The `updates` array passed to this function is generated by `extract_update_record_prices`, which inserts `0` for assets omitted from the update mask. Because an explicitly submitted `0` price (e.g., an asset losing all value) is also flattened to `0`, it becomes indistinguishable from an omitted update. Consequently, the zero price is neither emitted as an event nor recorded in the history mask (due to `if price > 0` in `mapping::update_history_mask`), forcing consumers to fall back to the last known non-zero price.

## Finding 6
- Pattern: Missing time-sequence validation
- Severity: HIGH
- Location: oracle/src/price_oracle.rs:431
- Description: set_price allows recording older or duplicate timestamps, unconditionally shifting the history bitmask and corrupting historical price lookup mapping.
- Evidence: In set_price, the timestamp is validated against ledger_timestamp but not against the last recorded timestamp. If an update has timestamp <= last_timestamp, prices::update_history_mask calculates update_delta as 0 but still unconditionally shifts the history bitmask left by 1 for every asset via mapping::update_history_mask. However, prices::store_prices explicitly avoids updating last_timestamp for older records. Since historical period indices are calculated as (last_timestamp - queried_timestamp) / resolution, this unrecorded shift causes all subsequent historical price queries to read the wrong bitmask position, silently corrupting or hiding price history.

## Finding 8

- Severity: HIGH

If an upgrade is scheduled but the WASM is temporarily downgraded, `at_latest_protocol_version` evaluates `protocol == CURRENT_PROTOCOL` and returns early without resetting `UPDATE_TS_KEY`. When a new upgrade starts, line 44 (`if scheduled_update_ts + timestamps::days_to_milliseconds(1) < ledger_timestamp`) evaluates to true immediately using the stale timestamp.

## Finding 9
- Pattern: Time-state update inconsistency
- Severity: MEDIUM
- Location: oracle/src/assets.rs:148
- Description: Missing expiration records are incorrectly granted an extra 'initial_expiration_period' on top of the paid bump, causing inconsistent TTL extensions compared to expired records.
- Evidence: On lines 148-150, missing records are assigned `now + initial_expiration_period` via `unwrap_or_else`. Because this value is in the future, it bypasses the reset to `now` on lines 152-154. Line 156 then adds the paid `bump`. As a result, missing records receive `initial_expiration_period + bump`, while existing expired records are reset to `now` and only receive the paid `bump`.

## Finding 10
- Pattern: Overloaded sentinel value
- Severity: MEDIUM
- Location: oracle/src/mapping.rs:24
- Description: update_history_mask overloads `price <= 0` as a sentinel for missing updates, which causes legitimately recorded zero or negative prices to be dropped from the history mask.
- Evidence: In oracle/src/prices.rs, extract_update_record_prices drops the explicit `update.mask` and injects a sentinel `0` into the array for un-updated assets. Subsequently, oracle/src/mapping.rs line 24 checks `if price > 0` to determine if the history bit should be set. If a legitimate price update of `<= 0` is supplied, it is conflated with the sentinel value and silently skipped. Consequently, the history mask is corrupted because `has_price` will return `false`, causing `retrieve_asset_price_data` to ignore the valid, stored update.

## Finding 11
- Pattern: Inconsistent sentinel validation
- Severity: MEDIUM
- Location: oracle/src/timestamps.rs:14
- Description: The `is_valid` function incorrectly evaluates the sentinel value `0` as a valid timestamp because `normalize(e, 0)` returns `0`. This causes `0 == 0` to return `true`, breaking the expected behavior of the validation function.
- Evidence: In `oracle/src/timestamps.rs`, `normalize` returns `0` when `value == 0` or `timeframe == 0`. The function `is_valid` checks `value == normalize(e, value)`. For an input `value` of `0`, this logic evaluates to `0 == 0`, returning `true`. This logic flaw requires callers to manually bypass it, as seen in `oracle/src/price_oracle.rs` line 441 where `set_price` must explicitly check `timestamp == 0 || !timestamps::is_valid(e, timestamp)` to safely reject the sentinel value.
